# Session Log — 2026-08-12

## Summary

Markd's verification emails had started landing in spam. Root cause was bot signups: `/signup` had
no rate limit, CAPTCHA or honeypot and mailed a verification link to whatever was typed in the box,
so bots drove hundreds of emails to nonexistent and trap addresses and the hard bounces dragged
`appfoundry.cc`'s sending reputation down.

Built a five-layer signup gate, shipped it as v58, and started moving transactional mail to a
dedicated subdomain. One commit, on `main`, deployed and verified live.

## Changes

### Signup gate (`1a6bf23`) — shipped as v58

New `Web/antispam.py` holds the defences; `Web/app.py` signup route rewritten to run them in order,
cheapest first:

1. **Honeypot + timing trap** — off-screen `website` field plus a signed "form served at T" stamp;
   rejects a filled honeypot or a submit under 2.5s.
2. **Rate limits** — DB-backed (`RateEvent`), split into a loose attempt counter (15/hr/IP) and a
   tight mail-sending counter (3/hr, 10/day per IP).
3. **Address validation** — strict regex, disposable-domain blocklist, live MX lookup (`dnspython`).
4. **Turnstile** — verified server-side via `urllib`, inert until keys are configured.
5. **Global cap** — 40 emails/hour enforced inside `_send_email`.

Supporting work:

- `POST /webhooks/resend` — Svix-signed bounce/complaint handler. Suppresses the address
  (`SuppressedEmail`) and deletes the unverified account behind a hard bounce.
- `Web/purge_stale_signups.py` — daily cron; clears never-verified accounts, expired tokens, old
  rate rows. Supports `--dry-run`.
- `ProxyFix` on the WSGI app, `limit_req` on the auth routes in `deploy/nginx-markd.conf`.
- "Send it again" on `verify_pending.html` — there was previously no resend-verification route.
- `/diagnostics` gained a "Signup gate & mail reputation" panel.
- `EMAIL_FROM` default moved to `mail.appfoundry.cc`; `setup.sh` seeds the three new env keys.

Verified with 37 assertions across two throwaway suites (traps, forged tokens, address validation,
rate caps, Turnstile rendering and enforcement, webhook signature/replay/transient-bounce handling),
then confirmed live: `/version` → `v58`, honeypot and `form_token` present on the served page.

## Decisions

- **Two separate signup rate counters, not one.** A single tight counter would lock out a real user
  who fat-fingers their address three times. The loose one stops hammering; the tight one only
  counts signups that actually put mail on the wire, which is the thing that damages the domain.
- **Layer 1 fails silently** — a tripped honeypot or timing trap returns the same "check your email"
  page a real signup gets, so a bot can't distinguish a block from a success and tune against it.
- **Turnstile fails *closed*, MX validation fails *open*.** A CAPTCHA that silently disables itself
  when Cloudflare is unreachable is a gate that looks fine while passing everything. DNS is the
  opposite: a resolver blip must not lock real users out of signup, so only a definitive NXDOMAIN
  or no-mail-records answer rejects.
- **The global cap lives inside `_send_email`, not the signup route.** Per-IP limits don't stop a
  distributed botnet; a cap on total outbound mail does, and putting it at the single choke point
  means no code path — present or future — can bypass it.
- **Turnstile and the webhook are env-gated.** Everything that needs no external setup ships and
  works immediately; the two pieces requiring Derek's accounts activate when keys appear.
- **Moved app mail to `mail.appfoundry.cc` rather than repairing `appfoundry.cc` in place.** Starts
  clean instead of waiting out the damage, and insulates the root domain. Free, because Markd is the
  only sender on that Resend account — see the caveat below.
- **Deployed the gate before the domain move.** Verifying a fresh subdomain while `/signup` was
  still open would have burned the new domain's clean reputation immediately.

## Notable discoveries

- **`ProxyFix` was missing and would have made the whole exercise pointless.** Nginx proxies over a
  unix socket, so without it every request looks like it came from the same place and per-IP rate
  limiting silently does nothing. Anything IP-based here depends on it.
- **Resend's free plan verifies exactly one domain**, so the subdomain move is a *swap*, not an
  addition — and the DKIM key is only revealed after a domain is added, so records can't be staged
  in advance. There is an unavoidable 10–60 minute window with no sending. Documented in
  `deploy/README.md` step 1.
- **`appfoundry.cc` is a shared multi-project Cloudflare zone** (`havlist`, `jukebox`, `markd`,
  `menuvi`, `photostream`, `regoreminder`). A root-level `v=spf1 -all` or `p=reject` would apply to
  every project under it, not just Markd. Do not tighten the apex without checking what else sends.
- **DMARC reports to an off-domain mailbox need that domain's permission** —
  `appfoundry.cc._report._dmarc.watsonblinds.com.au TXT "v=DMARC1"` — or most reporters drop them
  silently. Using an `@appfoundry.cc` address sidesteps it.
- **`sp=` on the root DMARC record is insurance, not load-bearing.** A subdomain's own `_dmarc`
  record takes precedence, so the root policy doesn't reach `mail.appfoundry.cc` once its record
  exists. (Corrected mid-session; had overstated this earlier.)
- **DMARC isn't actually required at this volume** — the Google/Yahoo bulk-sender rules start at
  5,000 messages/day and Resend already supplies SPF and DKIM alignment. Worth having anyway, mainly
  for the aggregate reports, which are the only direct read on whether reputation is recovering.
- **`EMAIL_FROM` was probably never set in the live `.env` at all**, meaning the app had been
  running on `app.py`'s default — and the v58 deploy therefore changed the sending address by
  itself, since that default moved to `mail.appfoundry.cc` in the same commit.

  Established by inode check: `/var/www/markd/.env` (330451) and `/var/www/markd/Web/.env` (274997)
  are **two distinct files**, not links. Only `Web/.env` is read — the systemd unit's
  `EnvironmentFile` points there; the root one is a pre-restructure stray. But `Web/.env` already
  held the new value, with an mtime minutes after the v58 deploy and well before Derek edited
  anything, and it is the larger of the two — consistent with `ensure_env` (`setup.sh:56-63`)
  appending the key because it was absent. Unconfirmed whether `setup.sh` was actually run.

  Two process failures worth keeping, both mine. **I asserted the server's `.env` pinned
  `EMAIL_FROM` without ever reading it**, inferring it from `.env.example` in git, and repeated that
  as the reason deploying couldn't affect sending. It landed on the right address by luck, not
  design. Then, when the root-path edit appeared to work, I called it the wrong file and sent Derek
  to redo it — the systemd path was right, but that never established the two paths were distinct.
  **Check live config against the running process (`/diagnostics` reports the sending address), not
  against paths or repo files.**

  Cleanup: rename `/var/www/markd/.env` out of the way. It's inert while `Web/.env` exists, but
  `setup.sh:28-33` would promote it if `Web/.env` ever went missing.
